## Часть 2. Качество описания ветки
В текущем описании ветки указано только «сделал игру». Непонятно, какие шаги нужны для проверки и были ли обнаружены ограничения.

### Шаблон хорошего описания ветки (Pull Request)
* **## Что сделано:** Краткое описание добавленных фич, измененных модулей или исправленных багов.
* **## Зачем:** Ссылка на задачу/issue и бизнес-требование (какую проблему решаем).
* **## Как проверить:** Пошаговая инструкция для ревьюера (какой скрипт запустить, какие входные данные ввести).
* **## Что осталось / Известные ограничения:** Описание компромиссов, нереализованных крайних случаев или планов на будущее.
* **## Чек-лист:** Минимальные требования перед слиянием (тесты пройдены, линтер не ругается).

## Часть 3. Лишние файлы
В ветке обнаружены следующие файлы, которых там быть не должно:
* `__pycache__/` — директория с компилированным байт-кодом Python. Должна быть добавлена в `.gitignore`, так как она генерируется автоматически на каждом устройстве.
* `.DS_Store` — системный файл macOS с настройками папки. Засоряет репозиторий, индивидуален для каждого пользователя.
* `черновик.md` — личные заметки автора. Вся рабочая документация должна находиться в README или удаляться перед коммитом.
* `todo.txt` — список задач. Для этого следует использовать инструмент Issues на GitHub или Task-трекеры.

## Часть 6. Этика обратной связи

### 5 правил этичной обратной связи:
1. **Критикуй код, а не человека:** Заменяй фразу «Ты написал плохой цикл» на «Этот цикл работает бесконечно».
2. **Будь конкретен:** Всегда указывай точный файл, номер строки и сценарий, при котором возникает проблема.
3. **Объясняй «почему»:** Не просто пиши «переделай», а объясняй последствия (например: «программа упадет, если...»).
4. **Предлагай варианты решений:** Помогай автору развиваться, делясь ссылками на документацию или примерами конструкций (например, `try/except`).
5. **Хвали за хорошее:** Обязательно отмечай удачные архитектурные решения, понятные названия функций или чистоту структуры.
